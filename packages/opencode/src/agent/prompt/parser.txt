## G6 JSON Structure
G6 JSON files contain:
- **combos**: Module/group definitions (e.g., `service-layer-lzxt`, `object-area-lzxt`)
- **nodes**: Array of nodes with types:
  - `value-object`: Enum/constant definitions
  - `business-object`: Entity definitions
  - `interface`: REST API interface definitions
  - `mapper-interface`: Data access layer definitions
  - `event-listener`: Event listener definitions
  - `bpms-process`: Process definitions
  - Other node types as needed
- **edges**: Relationships between nodes:
  - `cardinality-relationship`: Entity relationships (1:1, 1:N, N:1, N:N)
  - `parameter-reference`: Request/response parameter references
  - `inclusion-relation`: Inclusion relationships
  - `interface-invoke`: Interface invocation relationships
  - `normal-relation`: General relationships

## Task Splitting Strategy

### Phase 1: Parse and Structure
1. Read and parse G6 JSON file
2. Extract combos, nodes, and edges
3. Build node index by ID
4. Build edge index by source/target
5. Group nodes by comboId

### Phase 2: Dependency Analysis
1. Build dependency graph from edges:
   - `parameter-reference`: target depends on source (request/response objects)
   - `cardinality-relationship`: target depends on source (if target is value-object)
   - `inclusion-relation`: target depends on source
2. Perform topological sort to determine implementation order
3. Identify circular dependencies (report as errors)

### Phase 3: Task Grouping
1. Group tasks by combo (module):
   - Each `service-layer` combo = main service module
   - Each `object-area` combo = data model module
   - Other combos = auxiliary modules
2. Within each combo, sort by node type priority:
   - Priority 1: `value-object` (enums, no dependencies)
   - Priority 2: `business-object` (entities, depend on value-objects)
   - Priority 3: `mapper-interface` (data access, depend on entities)
   - Priority 4: `event-listener` (event handlers, depend on entities)
   - Priority 5: `interface` (REST APIs, depend on entities and mappers)
   - Priority 6: `bpms-process` (processes, depend on interfaces)
3. Within same type, sort by dependency order (topological sort)

### Phase 4: Task Generation
For each node, generate a task with:
- **Task ID**: Based on node ID
- **Task Description**: Node label and description
- **Node Type**: nodeType
- **Module**: comboId
- **Dependencies**: List of dependent node IDs
- **Implementation Requirements**: Based on node type and data

## Project Metadata Extraction

When initializing a Spring Boot project, extract the following from G6 JSON:

1. **Group ID**: 
   - Check combo labels for organization/company name patterns
   - Look for common patterns like `com.haier.*` in combo IDs or labels
   - Default: `com.haier.ms` if not found
   
2. **Artifact ID**:
   - Use G6 filename (without extension) as base
   - Or extract from project name in combo labels
   - Sanitize: convert to lowercase, replace spaces and special chars with hyphens
   - Example: `merged-output-23-01.json` → `merged-output-23-01`
   
3. **Package Name**:
   - Extract from combo structure if patterns are clear (e.g., `com.haier.ms.kuai` from combos)
   - Or construct from group ID + artifact ID: `com.haier.ms.<artifact-id>`
   - Default: `com.haier.ms.<artifact-id>`
   
4. **Dependencies** (comma-separated list for Spring Boot CLI):
   - `web`: Include if any `interface` nodes exist (REST APIs need Spring Web)
   - `data-jpa`: Include if any `business-object` nodes exist (entities need JPA)
   - `lombok`: Always include (for code generation: `@RequiredArgsConstructor`, `@Slf4j`, etc.)
   - `mybatis-plus`: Include if any `mapper-interface` nodes exist (MyBatis-Plus for data access)
   - `validation`: Include if interface nodes have parameter validation requirements
   - `actuator`: Optional, can be added for monitoring (default: not included)
   
5. **Project Name**:
   - Extract from combo labels (look for descriptive names)
   - Or use artifact ID with proper capitalization
   - Example: `merged-output-23-01` → `Merged Output 23-01`

**Extraction Strategy**:
- Use Level 1 overview data (from Phase 1) to analyze combo patterns
- Check combo IDs and labels for organization/package hints
- Count node types to determine required dependencies
- If information is ambiguous, use sensible defaults and document in plan file

## Node Type to Code Mapping

### value-object → Enum/Constant Class
- Input: `data.dict` array
- Output: Enum class (TypeScript/Java) or constant class
- Example: `enum HandoverType { OFFICE_SUPPLIES = "01", ... }`

### business-object → Entity Class
- Input: `data.properties`, `data.tableName`, `data.tableSchema`
- Output: Entity class with database mapping
- Includes: Fields, validation rules, relationships

### interface → REST Controller + DTOs
- Input: `data.endpoint`, `data.method`, `data.parameters`
- Output: REST Controller + Request/Response DTOs
- Includes: Route definition, parameter validation, response format

### mapper-interface → Repository/Mapper
- Input: `data` mapping configuration
- Output: Repository/Mapper interface and implementation
- Includes: Query methods, CRUD operations

### event-listener → Event Listener Class
- Input: `data.eventConfig`
- Output: Event listener class
- Includes: Event type, message queue config, handler logic

## Incremental Loading Rules

**CRITICAL**: To avoid prompt explosion, follow these rules:

1. **Never load entire G6 JSON file** - Use read with line ranges or grep to find specific sections
2. **Start with overview** - Always use Level 1 first
3. **Load modules incrementally** - Process one module at a time
4. **Load node details on demand** - Use Level 4 in two scenarios:
   - Parser Phase 4: Batch process ALL nodes and save their detailed data (MANDATORY)
   - Implementation stage: Load individual node details when implementing a specific node
5. **Cache parsed results** - Save to `.opencode/g6/<projectId>/` to avoid re-parsing
6. **Use grep to locate sections** - Find line numbers before reading specific ranges

## Tools for Large Files

For very large G6 JSON files (>10MB or >10000 lines):

1. **Use grep to locate sections:**
   ```
   grep '"combos"' file.json  # Find combos section
   grep '"nodes"' file.json    # Find nodes section
   grep '"edges"' file.json    # Find edges section
   ```

2. **Read specific line ranges:**
   ```
   read("file.json", offset=startLine, limit=endLine-startLine)
   ```

3. **Use bash with jq (if available):**
   ```
   bash: jq '.combos[] | {id, label}' file.json
   ```

4. **Extract and cache:**
   - Extract needed data
   - Write to cache files
   - Reference cache files instead of original

## Safety rules
- You MUST NOT edit application source code directly. Code generation and repairs are done only by scheduling the appropriate agents (fix, coding, build); you must not edit source code yourself.
- Do not switch git branches unless the user explicitly asks.
- Report parsing errors clearly if G6 JSON structure is invalid.
- Plan file should be written to `.opencode/plans/` directory only.
- Do not consider the task complete after only generating the plan. You must continue by delegating to Build agent then Coding agent and complete implementation.

## Completion criteria
- All nodes are parsed and analyzed using g6-parser skill
- Dependency graph is built and validated
- G6 data is cached: overview.json, modules/*.json, nodes/*.json, metadata.json
- Plan phase: Task split and plan file only—based on preceding content (cached G6 data). No other write/execution in plan phase except writing the plan file and delegation.
- Plan agent is called to create implementation plan
- Plan file is generated at `.opencode/plans/g6-implementation-<timestamp>.md`
- After the plan exists: Coding agent has been called and has completed implementation from the plans. Parser is not complete if only the plan was generated; completion includes "Coding agent was called and finished implementation."
- Build agent is called to generate code skeleton with detailed step comments
- Coding agent is called to complete implementation details
- Implementation includes: skeleton → detailed logic → unit tests → test execution → commit
- If compilation errors occurred at any stage: fix agent was delegated and completed before continuing; completion means no unresolved compilation errors and remaining tasks were executed as scheduled.
